# ManusとClaude Codeを併用する手順

サイトの土台と公開はManus、細かい修正やAPI連携はClaude Code、という分担で進めるための運用ルール。

---

## 大原則：GitHubのmainが唯一の正

ManusもClaude Codeも、**GitHubのmainブランチを共通の置き場**として同期する。
どちらかが勝手に持っている「別バージョン」を作らないことが、事故を防ぐ唯一の方法。

```
        ┌──────────────┐
        │  GitHub main │  ← ここが常に正しい状態
        └──────┬───────┘
         取り込み ↕ 反映
   ┌───────────┴───────────┐
   │                       │
┌──▼───┐               ┌───▼──────┐
│ Manus│               │Claude Code│
│画面・ │               │ API連携・ │
│デプロイ│               │ 修正・検証 │
└──────┘               └───────────┘
```

### 絶対に守ること

**同時に作業しない。** どちらか一方が作業している間、もう一方は触らない。
両方が同じファイルを別々に編集すると、後から取り込んだ側が相手の変更を消してしまう。

## 1. Manusへの乗り換え手順（最初の1回）

### ステップ1: 新しいプロジェクトを作る

前のプロジェクトは消えているため、Manusで新規作成する。

### ステップ2: GitHubリポジトリを接続する

`sei0520tg-ship-it/natulabo-portal` を接続する。
これで既存のコード（UIリニューアル・動画180本のデータ・自前ログイン）がすべて入る。

### ステップ3: データベースを用意し、環境変数を設定する

| 変数 | 必須 | 内容 |
| --- | --- | --- |
| `DATABASE_URL` | ○ | Manusが用意するDBの接続情報 |
| `JWT_SECRET` | ○ | 32文字以上のランダム文字列。`openssl rand -base64 48` で生成できる |
| `YOUTUBE_API_KEY` | | YouTube自動同期を使う場合 |
| `YOUTUBE_PLAYLIST_ID` | | 同上 |
| `EVENT_SHEET_CSVS` | | イベント連携を使う場合 |

**`OAUTH_SERVER_URL` は設定しない。** ログインを自前方式に置き換えたため不要。

### ステップ4: DBの構造を作る

```bash
pnpm run db:push
```

空のDBに対して実行するので、マイグレーションが最初から順に流れる。

### ステップ5: 最初の会員（＝管理者）を作る

1. DBに招待コードを1件入れる
2. サイトの `/register` から自分が最初に登録する
3. **最初の登録者は自動的に管理者になる**

### ステップ6: 動画180本を復元する

管理画面 `/admin/videos` の「180本をインポート」を押す。

### ステップ7: バックアップを取る

**ここを飛ばさない。** 前回はバックアップが無い状態でプロジェクトが消え、会員データを失った。

```bash
DATABASE_URL='接続情報' pnpm run db:backup
```

## 2. 日々の使い分け

| 作業内容 | 担当 | 理由 |
| --- | --- | --- |
| 画面のデザイン変更 | Manus | プレビューを見ながら直せる |
| 文言の修正 | どちらでも | |
| **YouTube API連携** | **Claude Code** | 認証・同期処理・エラー処理を書く必要がある |
| **イベントのスプレッドシート連携** | **Claude Code** | 同上 |
| 複雑なロジック・不具合調査 | Claude Code | テストを書いて検証できる |
| デプロイ・公開 | Manus | Publishボタンで完結する |

---

## 3. Claude Codeで作業するときの手順

### 開始時

「GitHubの最新を取り込んで作業を始めて」と伝える。Claude側で以下を行う。

```bash
git checkout main && git pull origin main
```

**Manusが直接mainへコミットしているため、必ず最初に取り込む。**

### 作業中

Claude Codeは作業用ブランチを作り、変更をPull Requestにする。
これによりManusの作業と混ざらず、後から何を変えたか追える。

### 終了時

PRをマージしてmainに反映したら、**Manusに取り込ませる**。
Manusのチャット欄に次を貼る。

```
GitHubのmainブランチに新しいコミットがマージされています。
GitHubから最新のmainを取り込んでください。
完了したら教えてください。
```

そのあと画面右上の **Publish** を押す。

---

## 4. Manusで作業したあとの手順

Manusは**mainへ直接コミットする**（`Checkpoint:` で始まるコミット）。
Pull Requestを経由しないため、レビューされないまま反映される。

そのため、Manusで大きな変更をしたあとは、Claude Codeに次を頼むとよい。

```
Manusがmainを更新しました。取り込んで、型チェックとテストが通るか確認して。
```

Claude側で `git pull` → `pnpm run check` → `pnpm test` を実行し、
壊れていないかを確認する。

## 5. 過去に実際起きた事故と、その対策

### マイグレーションの採番が衝突した

私（Claude）とManusが別々に採番した結果、`idx=6` のマイグレーションが2つできた。
さらに中身が重複しており、そのまま流すと必ずエラーになる状態だった。

**対策済み**：`server/migrationOrder.test.ts` が以下を検証する。

- `idx` の重複が無いこと
- `idx` が0から連番であること
- journalの各エントリに対応する `.sql` が存在すること
- 同じカラムを二重に追加していないこと

`pnpm test` を実行すれば検知できる。**DBの構造を変えたあとは必ずテストを走らせる。**

### バックアップが無いままプロジェクトが消えた

会員データと視聴進捗を失った。動画180本はコードに残っていたため復元できた。

**対策**：`pnpm run db:backup` を月1回。バックアップはGitHub以外の場所に保管する。

## 6. 困ったときの合言葉

| 状況 | Claudeに伝える言葉 |
| --- | --- |
| Manusが何か変えた | 「Manusがmainを更新しました。取り込んで確認して」 |
| 動かなくなった | 「動かないので原因を調べて」 |
| バックアップしたい | 「DBのバックアップを取りたい」 |
| 見た目を確認したい | 「ローカルで起動して確認させて」 |
| 公開URLが欲しい | 「確認用の公開URLを出して」 |
